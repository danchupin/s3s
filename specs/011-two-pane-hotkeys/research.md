# Research: s3s Feature 011 — Three-Zone Master-Detail Browse + Hotkey Mnemonic Review & Bold Glyphs

**Phase 0** · Branch `011-two-pane-hotkeys` · Constitution v1.0.0 (no amendment) · Touches Principles I (Core/UI separation — UI uses the read-only `storage.Storage` interface only), II (non-blocking TUI), III (test-first white-box `package ui`). No new write-S3 symbols; `check-readonly` stays green.

This document resolves the open implementation choices for two coupled scopes: **(A)** a three-zone (buckets | objects | details) master-detail browse at the Full layout tier, collapsing to Dual then to the current single-column mode-stack; and **(B)** a hotkey mnemonic review (remove only the global AddConn `n`) plus bold key glyphs everywhere advertised keys render, with an NO_COLOR-safe non-color cue. Every decision is anchored to existing code and reuses the established non-blocking, cache, debounce, layout, and keymap machinery — no new storage method, no new hue, no new generation discipline.

## Decisions

### R1 — Objects-zone load wiring (bucket-selection change → live level load)

- **Decision**: When the bucket cursor settles on a real bucket in the objects-capable layout (Full/Dual), trigger a level load for `(bucket, prefix="", search="")` by reusing the EXISTING `loadLevel(ctx, st, key, q, gen)` command (`commands.go:62`) → `levelMsg` (`messages.go:19`) → `onLevel` (`tree.go:188`). The cache key is assembled by the existing `levelKeyFor(bucket, "")` helper (`app.go:330`), which builds `cache.Key{Context: m.ctxName, Bucket: bucket, Prefix: "", Search: ""}` — identical to what `enterLevel`/`levelKey` produces for the top level of a bucket (`app.go:323`). The objects zone therefore shares cache entries with the full-screen tree view: a level previewed in the objects zone is a cache hit when the user later crosses into it, and vice-versa (FR-006e). No new command, no new message, no new storage method — `ListLevel(bucket, prefix="", ...)` is the only call (FR-026/FR-027), so the read-only guard stays green.
- **Rationale**: `enterLevel` (`tree.go:116`) already does exactly this sequence (cache `Get` → on miss `beginLoad` + `loadLevel` under the bumped gen, on hit serve `m.level = cached` with `loading=false`). The objects-zone fetch is the same flow minus the `m.mode = modeTree` flip — the result must populate a *secondary* level view, not take over the screen. `onLevel` already merges pages and calls `m.cache.Put(msg.key, m.level)` (`tree.go:200`), so success+empty caching is free (FR-006b). The cache is keyed precisely (`cache.go:9`) and shared across the session.
- **Alternatives considered**: (a) A separate `objLoadLevel`/`objLevelMsg` pair with its own `objLevelState` — rejected: duplicates `loadLevel`/`onLevel`/`levelState` and forks the cache key assembly, risking drift and double-fetches when the objects-zone and tree views key the same level. (b) A separate `m.objLevel *levelState` + `m.objSelKey` distinct from `m.level` — **superseded by R6**: the objects zone reuses `m.level` directly (focus, not a second level state, is what distinguishes the buckets zone from the objects zone), and a stale objects-zone result for a scrolled-past bucket is dropped by the existing load-gen guard in `onLevel` (`if msg.gen != m.gen`, `tree.go:189`) together with the `bucketLoadGen` debounce — so no second level state is needed.

### R2 — Debounce on bucket scroll (settled-selection fetch only)

- **Decision**: Reuse the existing pane debounce mechanism for the objects-zone load. The constant is `paneDebounce = 180 * time.Millisecond` (`commands.go:302`) — within the ≤200 ms ceiling (FR-003). On each bucket-cursor move in an objects-capable tier, bump `m.bucketLoadGen` and schedule a `tea.Tick(paneDebounce, …)` carrying `(gen, bucketName)` — mirroring `paneTickCmd(gen, key)` (`commands.go:312`) and `afterSelectionMove` (`app.go:291`). The settle handler (mirroring `onPaneTick`, `app.go:307`) fires the level load into `m.level` only if `msg.gen == m.bucketLoadGen && msg.key == currentBucketName`; a tick for a scrolled-past bucket is dropped. The in-flight `loadLevel` itself carries the load gen from `beginLoad` (`app.go:265`), so even a fired-but-superseded fetch is discarded at `onLevel`'s `if msg.gen != m.gen` guard (`tree.go:189`).
- **Rationale**: This is the proven double-suppression already used for the details pane: a debounce tick gated by `(gen, key)` equality (suppresses scheduling churn) *plus* a generation check on the result message (suppresses an in-flight superseded fetch). `onPaneTick` is the exact template — fast scroll through buckets schedules many ticks but only the one matching the settled `(bucketLoadGen, bucketName)` survives, so exactly one `ListLevel` is issued for the settled selection (FR-003, verified against `pane_test.go` debounce assertions).
- **Alternatives considered**: (a) A new, longer debounce constant for buckets — rejected: 180 ms is already proven comfortable for the pane's HeadObject+GET pair, which is heavier than a single first-page `ListLevel`; a second constant is needless surface and risks exceeding the 200 ms ceiling. (b) No debounce, load on every bucket-cursor move — rejected: violates FR-003 (fast scroll would issue one `ListLevel` per intermediate bucket) and the non-blocking spirit of Constitution II.

### R3 — First-page size for the lazy objects-zone preview

- **Decision**: Issue the objects-zone fetch with `storage.LevelQuery{Bucket: b, Prefix: "", Search: ""}` leaving `MaxKeys` zero, which the client resolves to `DefaultMaxKeys = 1000` (`storage.go:210`, applied in `fake.go:108` and `s3client.go:103`). The objects zone renders only the rows that fit its window via the existing `windowBounds(n, sel, rows)` (`styles.go:192`); paging on demand reuses `fetchNextPage` (`tree.go:133`) only when the user focuses the objects zone and scrolls to the last loaded row with `!m.level.complete` (the same gate `onTreeKey`'s Down branch uses, `tree.go:55`).
- **Rationale**: The codebase has exactly one page-size knob — `LevelQuery.MaxKeys` with a `DefaultMaxKeys` of 1000 (`storage.go:168`/`:210`). The objects zone needs only "the first page" for a preview; the first page IS one `ListLevel` call with the default cap, identical to `enterLevel`'s first fetch. There is no smaller fixed "preview page" concept anywhere in storage, and inventing one (e.g. `MaxKeys: 50`) would diverge the objects-zone cache entry from the tree view's first-page entry (same `cache.Key`, different contents) — breaking the shared-cache invariant from R1. Keeping the default page means a cross-into-objects (R7) is a guaranteed cache hit.
- **Alternatives considered**: (a) A small `MaxKeys` (e.g. 50) tuned to the visible window — rejected: it would make the objects-zone entry and the tree-view entry for the same `(bucket,"")` key hold different data, so crossing in (R7) would either show a truncated list or force a re-fetch, defeating FR-006e and FR-006a's "first page fetched for preview, paging on demand." (b) Fetching all pages eagerly for an accurate count — rejected: violates the lazy/non-blocking mandate (FR-002a/FR-006a, Constitution II).

### R4 — Error-not-cached policy (errors re-attempt on revisit)

- **Decision**: Keep caching exactly where it is today — `onLevel` calls `m.cache.Put(msg.key, m.level)` ONLY on a successful `levelMsg` (`tree.go:200`). A listing failure produces `errMsg`, not `levelMsg` (`commands.go:65`: `return errMsg{gen, err}`), and `errMsg` handling (`app.go:393`) never touches the cache. Therefore a failed/denied objects-zone listing is never cached: the next settle on that bucket re-issues `loadLevel` (cache `Get` misses) and re-attempts (FR-006b/c). The objects zone must apply the SAME branch — route its failure through `errMsg`, never synthesize an empty `levelState` and `Put` it. A success-but-empty page IS cached (an empty `levelState` is a valid `levelMsg` result), which is correct: "no objects here" is a real, cacheable answer.
- **Rationale**: The success/error split is already structural — only `loadLevel`'s happy path emits `levelMsg`, and only `onLevel` writes the cache. There is no code path that caches an error. The objects zone gets correct error-revisit semantics for free by reusing `loadLevel`/`onLevel` unchanged (R1). The `storage.Fake` test knobs `FailListBuckets` and `AccessDeniedBuckets` (`fake.go:23`/`:26`) let a white-box test seed a denied bucket, assert no cache entry, and assert a second settle re-issues `ListLevel` (via `ListLevelCalls`, `fake.go:31`).
- **Alternatives considered**: (a) Caching a sentinel "error level" to avoid re-hammering a denied bucket — rejected: violates FR-006b/c (errors must re-attempt on revisit) and the cache doc's "freshness is user-driven" contract (`cache.go:5`); a transient 403 (creds refreshed elsewhere) would stay stuck until a manual `r`. (b) A short error TTL — rejected: the cache is deliberately TTL-free (`cache.go:4`); adding expiry for one case forks the cache model.

### R5 — Three-zone layout composition, width math, and height budget

- **Decision**: Generalize the existing two-box composer `listWithPane` (`app.go:935`) into three layout tiers driven by `clampW(m.width)`:
  - **Single (`w ≤ 99`)**: the current single-column mode-stack — `boxView(title, sel, renderList(w-2, dataRows), w, rows)` exactly as today (`app.go:937`). This is the existing `w < paneSplitMin` branch (`paneSplitMin = 100`, `app.go:929`), unchanged.
  - **Dual (`100 ≤ w ≤ 129`)**: buckets | objects. The details pane collapses. Reuse the proven pane split arithmetic but for the *objects* box: `paneW := w/3` clamped to `[24, 40]` (`app.go:939–945`) sized for buckets-or-details, and give the larger remainder to objects. Concretely: left buckets box `bucketsW` clamped `[24,40]`, objects box gets `w - bucketsW`; join via `lipgloss.JoinHorizontal(lipgloss.Top, …)` (`app.go:949`).
  - **Full (`w ≥ 130`)**: buckets | objects | details — three boxes. Buckets and details take the clamped `[24,40]` side widths; objects absorbs the middle remainder `w - bucketsW - detailsW`. Each box is a `boxView` with rounded borders (`styles.go:220`); join all three with a single `lipgloss.JoinHorizontal(lipgloss.Top, bucketsBox, objectsBox, detailsBox)`.
  - **Height budget**: unchanged. `View()` already computes `rows = m.height - footerH - 2` and `dataRows = rows - 2` (the 2-line table header) (`app.go:867–876`); every box passes `rows` as its `minRows` to `boxView`, which hard-caps the body to that height (`styles.go:233`) so the multi-line footer (incl. the command bar / hint line) never scrolls off. The details box continues to receive `rows-2` for its body height as today (`app.go:948`).
- **Rationale**: `listWithPane` already does the exact 2-box `JoinHorizontal` with the `w/3` clamp `[24,40]` and `listW = w - paneW` (`app.go:939–949`) — the three-tier version is a generalization of one already-working split, not new layout code. `windowBounds` makes each zone's scrolling stateless from its own cursor (`styles.go:192`), so resize reflow stays trivial (CLAUDE.md's "selection indices are the only state"). The `boxView` body hard-cap (`styles.go:233`) is the existing guarantee that the footer survives; reusing it per box means three boxes can't individually overflow. `lipgloss.JoinHorizontal(lipgloss.Top, …)` already aligns boxes of equal `rows` height.
- **Alternatives considered**: (a) A fresh layout function independent of `listWithPane` — rejected: would duplicate the clamp/`JoinHorizontal`/`boxView` wiring and the height-budget arithmetic that `View()` already feeds in. (b) Percentage widths (e.g. 25/50/25) instead of the `[24,40]` clamp — rejected: the existing clamp keeps side panes readable at 130 cols and not absurdly wide at 200 cols; matching it keeps the Dual→Full transition visually continuous and reuses proven constants. (c) Folding tier selection into `View()` instead of `listWithPane` — rejected: `View()` already delegates the buckets/tree body to `listWithPane` (`app.go:894–899`); keeping the tier branch there preserves the single composition seam and the existing `m.paneVisible` collapse toggle.

### R6 — Focus model state (focusZone + per-zone cursors)

- **Decision**: Add ONE small enum field `m.focusZone` (`zoneBuckets` | `zoneObjects`, default `zoneBuckets`) to `App`, plus ONE debounce counter `m.bucketLoadGen int` for the bucket→objects reload tick. The objects zone REUSES the existing level machinery wholesale: its content is `m.level` and its cursor is the existing `m.treeSel` (`app.go:124`). `focusZone` selects which cursor the nav keys move — `zoneBuckets → m.bucketSel`, `zoneObjects → m.treeSel`. Scrolling buckets (focus on buckets) debounces (`bucketLoadGen` tick) then `beginLoad`+`loadLevel` the highlighted bucket's level into `m.level`, resetting `m.treeSel = 0` exactly as `enterLevel` (`tree.go:118`). **Crossing focus does NOT load** — `m.level` already holds the highlighted bucket's level. `Update` branches on `m.focusZone` ONLY in objects-capable tiers (Dual/Full); in Single tier the existing `modeBuckets`/`modeTree` switch (`app.go:620`) is unchanged. The active zone gets the accent `boxView` border/title (`titleStyle`, `styles.go:263`); inactive zones use the dim default — no new style token (FR-007/008).
- **Rationale**: Reusing `m.level`/`m.treeSel` makes `selected()`, `afterSelectionMove()`, the pane debounce, `windowBounds`, `fetchNextPage`, and `enterLevel`/`goBack` all operate on the objects zone **verbatim** — the objects zone simply IS the level view, with `focusZone` deciding whether keys move the bucket cursor or the level cursor. There is no separate "preview vs crossed-in tree": at every tier the highlighted bucket's level lives in `m.level`; multi-pane just renders it beside the buckets instead of full-screen. The only genuinely new state is the focus selector + the bucket-reload debounce counter; everything else is existing machinery (this supersedes the earlier `objLevel`/`objSel` draft referenced in R1/R2/R3 — see the reconciliation note below).
- **Alternatives considered**: (a) A dedicated `m.objLevel *levelState` + `m.objSel int` separate from `m.level`/`m.treeSel` (an earlier draft of R1/R6) — rejected: it duplicates the whole level-navigation surface (cursor, paging, drill, clamp) and forks the cache write path, for a "preview vs full tree coexist" case that does not actually arise — the objects zone *is* the level; you never need both a preview and a separate full tree of the same bucket at once. (b) A `focusZone` with a third `zoneDetails` value — rejected: the details zone is non-interactive (it mirrors the focused row's preview, `pane.go:20`); `Tab` is a symmetric buckets↔objects toggle (FR-007), so two zones suffice. (c) Encode focus in `m.mode` (e.g. `modeObjectsZone`) — rejected: `mode` is the screen/overlay selector (`app.go:24`) consumed by `View()` and every modal guard; overloading it with intra-screen focus would entangle focus with overlay routing.

> **Reconciliation (post-analyze, 2026-06-07)**: R1/R2/R3 below were drafted with a separate `m.objLevel`/`m.objSel`/`m.objGen`. The canonical state model is R6 above — **reuse `m.level` + `m.treeSel`**, with `m.bucketLoadGen` as the only new debounce counter. Read the `objLevel`→`m.level`, `objSel`→`m.treeSel`, `objGen`→`bucketLoadGen` substitutions when applying R1–R3.

### R7 — Tab + cross/return key dispatch (focus-aware, single-tier-safe)

- **Decision**: Keys are matched today via `matches(key, m.keys.X)` (`keys.go:75`) inside per-mode handlers (`onBucketsKey` `app.go:636`, `onTreeKey` `tree.go:41`) and the catalog dispatch `dispatchActionKey`/`dispatchChord` (`commands.go:111`/`:144`). Insert focus-aware handling in the objects-capable tiers ONLY:
  - **Tab** (new `m.keys.Focus = []string{"tab"}`): symmetric `zoneBuckets ↔ zoneObjects` toggle. Matched in `onKey` *after* the modal guards (search/op/form/command, `app.go:527–576`) and *before* the `switch m.mode` (`app.go:620`), gated on the tier being Dual/Full — so Tab is inert in Single tier and never fires inside a text input.
  - **Right/`l`/Enter-on-bucket** (`m.keys.Enter = {"enter","right","l"}`, `keys.go:48`): when focus is `zoneBuckets`, "cross into objects" = set `m.focusZone = zoneObjects` (no level load — the objects zone already shows the settled bucket's first page from R1/R2). Enter on the objects zone opens the object/dir as `onTreeKey`'s Enter does today (`tree.go:78`).
  - **Left/`h`/Esc** (`m.keys.Back = {"esc","left","h"}`, `keys.go:49`): focus-aware ascend-or-return — when focus is `zoneObjects` at the top prefix, return focus to `zoneBuckets`; when inside a sub-prefix, ascend one level via the existing `goBack` logic (`tree.go:153`). When focus is `zoneBuckets`, Esc/Left behaves as today.
  - Route bucket-zone keys to `onBucketsKey` and object-zone keys to `onTreeKey` based on `m.focusZone`; in Single tier the existing `m.mode` switch routes unchanged (FR-009).
- **Rationale**: The keymap is single-source (`defaultKeys`, `keys.go:42`) and every surface (dispatch, hint bar, help) derives from it (CLAUDE.md), so adding `Focus` to `keyMap` (`keys.go:11`) and `defaultKeys` is the only place a new binding is declared — the command bar and help pick it up automatically via `m.keys.*`. `Enter`/`Back` already alias `right`/`l` and `esc`/`left`/`h` (`keys.go:48–49`), so "cross right / return left" maps onto existing bindings with no new keys — only the *handler* becomes focus-aware. Placing the Tab match between the modal guards and the mode switch in `onKey` (`app.go`) mirrors how `WriteToggle`/`Command` are matched there (`app.go:598–612`), so it can never intercept text entry.
- **Alternatives considered**: (a) A brand-new key for "cross into objects" (e.g. `o`) — rejected: `right`/`l`/`Enter` are the established "drill in" bindings (`keys.go:48`); reusing them keeps the mental model identical to the single-column drill-down and avoids stealing a mnemonic letter. (b) Handling Tab inside each per-mode handler — rejected: Tab is screen-level focus, not a per-mode action; matching it once in `onKey` (like quit/help/command) prevents duplicating the gate in `onBucketsKey` and `onTreeKey`. (c) Making Tab also cycle to details — rejected per R6 (details is non-interactive; FR-007 says symmetric two-zone toggle).

### R8 — Bold key glyphs + NO_COLOR-safe cue

- **Decision**: Advertised keys today render via `accentStyle` (foreground-only coral, `styles.go:47`) in three render paths: the hint catalog `renderHintRow` (`styles.go:337`), the help rows `helpLines` (`keys.go:128`, `accentStyle.Render(pad(keys,17))`), and the command-bar role map `roleStyle` (`commandbar.go:36`, where `roleRead → accentStyle`, `roleWriteActive → warnStyle`). Add `.Bold(true)` to the key glyphs in all three: define `keyStyle = accentStyle.Bold(true)` (and bold variants of `warnStyle`/`emptyStyle`/`ruleStyle` used as command-bar roles) and render the **key portion** bold while the **label** stays plain `dimCellStyle`. The deterministic NO_COLOR cue is the **bold attribute itself**: lipgloss strips the SGR color codes under `NO_COLOR` but preserves the bold SGR (`\e[1m`), so the key stays visually distinct from its label even with no color — exactly the "redundant non-color cue" the `styles.go:70` NOTE already promises (`▶` gutter, `✓` mark, `[RW]/[RO]` text, `error:`/`loading…` prefixes). The bold weight joins that family for keys (FR-019–025).
- **Rationale**: All advertised keys flow through `accentStyle` (read keys) or the command-bar `roleStyle` map (`commandbar.go:36`) — both are single sources, so bolding there bolds every hint-bar, command-bar, and help key without per-call-site edits. lipgloss's renderer (cell-based, per CLAUDE.md) emits bold as a standalone SGR independent of color; under `NO_COLOR` lipgloss drops `Foreground`/`Background` but keeps `Bold`, so the bold cue is deterministic and terminal-independent. The existing NO_COLOR NOTE (`styles.go:70`) establishes the project's "every color meaning has a non-color twin" rule; bold is the natural twin for "this is a key."
- **Alternatives considered**: (a) An underline cue under NO_COLOR — rejected: bold is already the conventional weight emphasis, simpler, and one attribute covers both color and no-color modes (no branch on the env var). (b) Bracketing keys like `[d]` for a textual cue — rejected: it widens every hint and fights the command-bar's tight `fitEntries` width budget (`commandbar.go:257`); bold adds zero display width. (c) Branching on `os.Getenv("NO_COLOR")` in the styles — rejected: lipgloss already strips color globally under `NO_COLOR`; a manual branch would duplicate and risk diverging from lipgloss's own detection.

### R9 — Remove the global AddConn `n` hotkey (keep the row path)

- **Decision**: Remove the global `AddConn` key dispatch in `onKey` — the block at `app.go:604`: `if matches(key, m.keys.AddConn) && m.connect != nil && (m.mode == modeBuckets || m.mode == modeTree) { return m.openConnections() }`. Keep the `AddConn` binding in the keymap as the *opener* of the connections manager where the bar already advertises it (`commandbar.go:191`/`:244` render `glyph(m.keys.AddConn[0])` labelled "connections"), but the canonical "+ add connection" affordance is the **row** in the connections list (`connections.go:103`: `connRows` appends `"+ add connection"`, selected via Enter on the last row at `connections.go:124–129`). The add-bucket pattern already mirrors this row-only model (`app.go:666` `openAddBucket` on the `"+ add bucket"` row). Removing the *global bucket/tree* `n` shortcut leaves the connections-manager entry (the bar's "connections" affordance) and the in-list "+ add connection" row fully intact, so no path to adding a connection is lost.
- **Rationale**: The "+ add connection" row already exists and is the discoverable, mode-local affordance (`connRows`, `connections.go:101–104`); the `y`/`ctrl+o` chords and other keys are explicitly kept. Removing only the global `n` dispatch (`app.go:604`) is a one-block deletion that does not touch `connRows`, `onConnectionsKey`'s Enter-on-last-row (`connections.go:124`), or the command-bar "connections" entry (`commandbar.go:191`). The bar opens the manager; the manager's row creates the connection — two intact, discoverable steps.
- **Alternatives considered**: (a) Remove the `AddConn` binding from the keymap entirely — rejected: the command bar uses `m.keys.AddConn[0]` to render and route the "connections" opener (`commandbar.go:191`/`:244`); deleting the binding would break that opener. Only the *global bucket/tree shortcut dispatch* (`app.go:604`) is removed; the binding remains the manager-opener key. (b) Keep the global `n` too — rejected by the feature's own DECIDED direction (AddConn `n` is the one hotkey removed) and FR-019: the row-only model removes the redundant global mnemonic, matching the "+ add bucket" precedent.

### R10 — Testing approach (white-box `package ui`; Fake call counters; no integration)

- **Decision**: White-box `package ui` tests using the existing harness: `deliver(m, msg)` (`app_test.go:22`), `press(m, s)` / `pressCmd` (`app_test.go:59`/`:63`), `viewOf(m)` (`app_test.go:75` → `m.View().Content`), and the `fakeConnector` (`pinned_test.go:69`). Drive a `storage.Fake` (`fake.go:17`) and assert on its call counters `ListBucketsCalls` and `ListLevelCalls` (`fake.go:31`):
  - **Startup lists only bucket NAMES, zero object listings**: after `New` + `Init` deliver, assert `f.ListLevelCalls == 0` (lazy — no level loaded until a bucket settles, FR-002a). For a pinned/scoped connection, also assert `f.ListBucketsCalls == 0` (existing pattern, `pinned_test.go:39`).
  - **≤1 object listing per fast scroll**: deliver a rapid sequence of bucket Down keypresses, then deliver the single matching `paneTickMsg`-analogue settle for the last bucket; assert `f.ListLevelCalls == 1` (debounce + gen suppression, R2/FR-003). A settle for a superseded `(gen,bucket)` must add zero calls.
  - **Zero listings on cache revisit**: settle bucket A (1 `ListLevel`), settle bucket B, re-settle bucket A; assert `f.ListLevelCalls` does not increment on the revisit (cache hit, FR-006e). Mirror `pinned_test.go:178`'s "refresh called ListBuckets 0 times" counter-assertion style.
  - **Layout tiers**: deliver `tea.WindowSizeMsg` at width 90 (Single), 115 (Dual), 140 (Full) and assert `viewOf` shows one / two / three bordered boxes respectively (count the `╭` rounded-corner glyphs from `boxView`, `styles.go:270`).
  - **Bold glyphs / NO_COLOR**: assert the rendered hint/command-bar/help key carries the bold SGR; under `NO_COLOR` assert color SGRs are stripped but bold remains (R8).
  - **No integration test** is added: there is NO storage contract change (no new method, no signature change), so the real-backend MinIO suite is untouched.
- **Rationale**: The `Fake` already exposes `ListBucketsCalls`/`ListLevelCalls` (`fake.go:31`) precisely for "assert N calls" tests, and 010 established the counter-assertion idiom (`pinned_test.go:39`/`:178`). The browse zones reuse `loadLevel`/`onLevel`/cache (R1) and the proven debounce (R2), so behavior is fully observable through `viewOf` and the counters without any backend. Constitution IV's integration mandate triggers only on a storage contract change; FR-026/FR-027 explicitly reuse the existing `ListLevel` read method, so the contract is unchanged.
- **Alternatives considered**: (a) Add a MinIO integration test for three-zone browse — rejected: no storage contract change means an integration test would only re-exercise the already-covered `ListLevel` path through the UI, adding flake surface (testcontainers Docker detection, CLAUDE.md) for zero new backend coverage. (b) Black-box (`package ui_test`) tests — rejected: the project's convention is white-box `package ui` driving the model directly with `deliver`/`press` and asserting internal counters/state (CLAUDE.md "Testing conventions"); the new focus/debounce state (`focusZone`, `bucketLoadGen`; objects cursor = reused `treeSel`) is most directly asserted white-box.
